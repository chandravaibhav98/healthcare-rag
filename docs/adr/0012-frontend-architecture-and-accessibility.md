# ADR-0012 — Frontend architecture, generated API client and accessibility gate

- **Status:** Accepted (Phase 6)
- **Date:** 2026-11-14
- **Plan ref:** `plan.md` §4 Phase 6 · **Risks:** R8 (output read as clinical advice), R10

## Context

The SPA has two audiences: anyone asking a question (the Query Assistant) and reviewers
and administrators (the dashboard). It shows clinical-looking text, so it must make the
evidence and its limits obvious, it must never show a malformed answer as validated, and
it must be usable with a keyboard and a screen reader.

## Decision

| Concern | Choice | Why / alternative |
| --- | --- | --- |
| Stack | React 19 + TypeScript (strict) + Vite, React Router, TanStack Query, React Hook Form + Zod, Tailwind CSS 4, Radix primitives in shadcn/ui-style components, Recharts | Plan §4 Phase 6. The components follow shadcn/ui's copy-in pattern (cva + tailwind-merge) and are written in the repo, not generated by its CLI |
| API client | `openapi-typescript` generates `src/api/generated/schema.d.ts` from `backend/openapi.json`; `openapi-fetch` is the thin client. `scripts/gen-client.*` regenerates; `lint` fails if the types are stale | A contract change breaks `tsc`, not production. Hand-written types would drift |
| Runtime validation | `/qa` responses are parsed with Zod before rendering; a validated answer must cite evidence | Types vanish at runtime; a proxy or version skew must not produce a "validated" badge on bad data |
| Tokens | Access token in memory only; refresh token in the httpOnly cookie (ADR-0008); a non-secret "signed in" flag in localStorage decides whether to try a silent refresh on load | No token in Web Storage (XSS); no failing refresh call for anonymous visitors |
| 401 handling | Middleware refreshes once (single flight) and retries the request; a failed refresh clears the session | Users are not logged out every 15 minutes |
| Same origin | `VITE_API_BASE_URL` empty by default; Vite (dev) and nginx (Phase 8) proxy `/api` | The SameSite=Strict refresh cookie works without CORS |
| Code splitting | Dashboard pages lazy-loaded; vendor chunks `react`, `forms`, `charts` | The assistant never downloads chart code |
| Evidence view | Client-side highlight of words shared by the cited chunk and the answer sentences that cite it, plus a number check | Explains the server's coverage and numeric checks; the server's `meta.signals` stay the source of truth |
| Escalation | `POST /api/v1/escalations` (contract 1.3.0) flags any answer for the review queue; notes are redacted | "Escalate for review" must be a real action, not a mailto link |
| Accessibility | WCAG 2.2 AA: landmarks and skip link, visible focus, labelled controls, errors linked with `aria-describedby`, Radix focus management for dialogs and tooltips, charts hidden from AT with the same data as a table, contrast-checked tokens in light and dark themes, reduced motion respected | Plan exit criterion |
| Accessibility gate | Unit tests run axe-core (serious/critical = fail). `e2e/audit/ui-audit.mjs` drives every screen against a real stack and runs axe (contrast included, both themes) and Lighthouse (≥ 95 required) | jsdom cannot check contrast; the browser audit can |

## Consequences

- Every screen reached Lighthouse accessibility 100 and best practices 100 against the
  real API, with no axe violations in either theme (docs/project/phase-6-report.md).
- The browser audit needs Chrome and a running stack, so it is not yet a CI job (OI-29).
- Recharts adds ~118 kB gzip, loaded only on dashboard pages.
