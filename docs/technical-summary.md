# Technical Summary: Healthcare Guidelines RAG Assistant

*For stakeholders. 2026-11-20. Synthetic corpus: not for clinical use.*

## 1. Problem

Clinicians, administrators and support staff need fast answers from standard guidelines
(infection prevention, PPE, vaccination). Searching documents by hand is slow and
different readers interpret them differently. A general chatbot is worse: it answers
fluently whether or not the guidance supports the answer.

**Goal:** a question-answering service that answers *only* from authoritative guideline
text, shows exactly where each sentence came from, checks every answer against that
evidence, and **declines** when the support is weak. Later it must plug into the
organisation's secure guideline repository.

## 2. Approach

| Decision | Why |
| --- | --- |
| **Extractive answers**: sentences are copied from the guideline, never generated | Nothing the system says is outside its sources; every sentence carries a citation `[n]` |
| **Independent validation** of every answer: does one cited passage cover the question's key terms, how strong is retrieval, and does **every number** (dose, temperature, interval) appear in the cited text | The answer is released (`validated`) only if the confidence reaches 0.6 and the numbers check; otherwise it is withheld (`needs_review`) and the best sources are shown |
| **Deterministic, offline index** (hashed embeddings, exact search) | The same corpus always gives the same index, byte for byte, on Linux and Windows, with no external AI service |
| **Human in the loop**: reviewers see every withheld or escalated answer, record a verdict and promote good examples to the test data | Errors become evaluation data; the system improves with use |
| **Production shape**: FastAPI service, React app, PostgreSQL, Docker, Kubernetes, CI/CD with quality gates | It can be operated, monitored, upgraded and rolled back like any other service |

What it is **not**: it does not reason across documents, summarise, or answer from
general knowledge. That is the price of being checkable.

**Delivered beyond the brief**

- An admin dashboard: KPIs, review queue, evaluation runs with the threshold sweep,
  index versions, audited settings, audit log.
- Accessibility at WCAG 2.2 AA.
- Measured performance: p95 179 ms with 50 concurrent users, 0% errors.
- Delivery and operation:
  - zero-downtime upgrades and index rollbacks on Kubernetes;
  - a release pipeline that publishes only tested images, with SBOMs;
  - alerting with a runbook;
  - a narrated demo video regenerated by code on every release.
- One command, `scripts/reproduce.sh`, re-derives every number above and the demo from
  a fresh clone.

## 4. Risks and limitations

| Risk | Impact | Mitigation in place | Still to do |
| --- | --- | --- | --- |
| **Near-domain false answers.** Two unanswerable questions were answered, for example a hepatitis **A** question answered from hepatitis **B** guidance | A plausible but wrong answer | Withheld answers go to review; the numeric check; a persistent disclaimer | Keep qualifiers such as "A" or "type 2" attached to their term; require the question's main concepts to appear in the same cited sentence; confirm on a new test set |
| **Paraphrased questions** validate less often (62% vs 83% for direct ones) | More "needs review" for lay wording | Synonym expansion | A semantic embedder (the main quality lever left) |
| **Single annotator** (the developer) wrote the test questions | The metrics may flatter the system | Strict protocol: dev and test separated, tuning on dev only, the first test set retired when it was overfitted | A second annotator on ≥ 20%, then clinician-written questions (RUNBOOK §4.7) |
| **Synthetic corpus** | Real guidance is longer, messier and changes over time | A swap seam, snapshot builds, a sign-off checklist (RUNBOOK §4) | Connect the real repository; re-annotate; re-tune |
| **Restricted documents** | Leaking restricted guidance to the wrong staff | Not applicable to the public synthetic corpus | Retrieval-time access filtering, designed in RUNBOOK §4.6, **required before any restricted document is indexed** |
| **Patient data typed into questions** | Privacy | Redaction before storage, no question text in production logs, 30-day retention | Verify in each environment (RUNBOOK §6.4) |

## 5. Decisions needed

1. **How to read SC2.** Literal Precision@5 cannot reach 0.65 on this corpus with
   honest relevance labels, even for a perfect system. Proposal (ADR-0001): report
   P@5 relative to its ceiling (72%) alongside Hit@5 (95%). The alternative, shrinking
   chunks until the number passes, would raise the metric without helping users.
2. **Approve ADR-0001 and ADR-0002** (relevance definition; composite confidence). Both
   are implemented and evidenced, and await sign-off.
3. **False-validation tolerance** for any pilot, for example ≤ 1% for clinical users,
   which would set the threshold. The same evaluation tooling supports any target.

## 6. Next steps (recommended order)

1. Fix the two false-validation causes (§4), measured on a **new** held-out test set
   with a second annotator.
2. Pilot with the real repository behind the `DocumentSource` seam, following
   RUNBOOK §4.1–4.9, including access filtering if any document is restricted.
3. Evaluate an offline semantic embedder behind the existing `Embedder` interface, to
   improve paraphrase handling while keeping the index deterministic.
4. Connect sign-in to the organisation's identity provider (OIDC).
